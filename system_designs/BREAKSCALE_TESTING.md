# Breakscale Workload Testing for System Designs

Breakscale is an open-source, deterministic discrete-event simulator for exploring how a proposed architecture behaves under offered load. It models finite component capacity, queueing, service-time variance, timeouts, retries, circuit breakers, rate limiting, cache hit rates, autoscaling and injected failures. It reports measured simulated latency percentiles, goodput, errors, drops, queue depth and utilisation.

- Simulator: [Breakscale](https://breakscale.tech/)
- Source: [workersio/breakscale](https://github.com/workersio/breakscale)
- MCP server guide: [Breakscale MCP](https://github.com/workersio/breakscale/blob/main/mcp/README.md)
- Native deterministic engine and presets live in `src/sim`; the upstream README demonstrates `new Engine(topology, seed)`, repeated `advance()`, then `snapshot()`.

## What this adds to this repository

Use Breakscale alongside Mermaid and Archify:
1. Design the system and explain its responsibilities in the HLD docs.
2. Translate the request path into Breakscale components and request edges.
3. Declare assumptions with provenance: requirement-derived, measured, or illustrative.
4. Run a deterministic workload at baseline and stepped load.
5. Inject a failure or change one control (cache hit rate, capacity, instances, retries, queue limit, etc.).
6. Record p50/p95/p99, goodput, error rate, offered load, queue depth, and utilisation.
7. Explain what broke first, why it broke, and the smallest change that improves the stated goal.

**Not a production load test:** Breakscale simulates a model. It does not send real network requests to your application, measure AWS/GCP instance performance, validate your database or SDK, or establish production SLO compliance. Use k6/Locust/Artillery/JMeter against a deployed test environment for that. Breakscale results are architecture experiments, not observed production measurements.

## Repository layout

- `breakscale/README.md` — setup, CLI usage and evidence rules.
- `breakscale/scenarios/` — reviewed scenario manifests and provenance.
- `breakscale/reports/` — JSON reports generated by a local runner (gitignored by default).
- `breakscale/scripts/` — reusable validation and report tooling.
- `breakscale/examples/` — optional native `.breakscale` designs after validating their schema against the selected Breakscale release.

The first scenarios focus on clear mappings to Breakscale's existing engine vocabulary: URL shortener cache-aside, rate-limited API, retry storm/circuit breaker, and async workers/message queue. Designs with no defensible engine mapping remain documented as not modelled rather than forced into a misleading topology.

## Metrics to explain in interviews

| Metric | Interview interpretation |
|---|---|
| Offered RPS | Traffic arriving, including work that may fail |
| Goodput RPS | Requests successfully completed |
| p50 / p95 / p99 | Request latency distribution, not an average |
| Error rate | Failure share; examine failure categories as well |
| Queue depth | Work waiting for finite service slots |
| Utilisation | Capacity pressure; high utilisation can amplify queue wait |
| Shed / timeout | Distinguish immediate rejection from work that outlives its caller |
| Cache hit rate | A capacity input for the origin, not just a cache metric |
| Consumer backlog | Async work accepted faster than workers can drain |

## Required report fields

Every report records:
- Breakscale source URL and pinned revision/tag used.
- Scenario ID and source HLD.
- Deterministic seed and simulation duration.
- Inputs, units and provenance for every numeric setting.
- Baseline and experiment changes.
- Raw system and per-node snapshot metrics.
- Pass/fail thresholds and an explanation of what the simulation does not include.

Never copy a result into the HLD as a measured production SLO. Call it a **simulated result** and retain the manifest so it can be replayed.
